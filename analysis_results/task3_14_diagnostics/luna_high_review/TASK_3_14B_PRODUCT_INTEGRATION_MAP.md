# Task 3.14b Product Integration Map

**Review date:** 2026-11-15  
**Scope:** Read-only inspection of the profile validator/schema representation, v4 rig-conformance compiler, artifact binding and current tests. No code, profile, manifest, state or test was edited or run in this pass.

## Finding

The mechanical evidence manifest is **not on the current compiler path**. The v2 profile validator checks profile self-hash, the measured rest-axis inventory and candidate identity, but does not require or load the 3.14b manifest/report. The separate mechanical conformance module verifies its finite isolated-probe catalog and constructs a diagnostic contract; it has no link to the 171-bone report. `compileV4RigConformanceRecipe` calls mechanical-probe validation only when `constraints.mechanicalPoseProbes` is supplied, and the emitted artifact records only that optional probe contract. A conforming artifact with no such probes can currently be emitted without any 3.14b manifest reference.

No standalone JSON Schema file for `vozual.rig-capability-profile` was found under `schemas/`; executable validation in `mobile/tools/rig-capability-profile.cjs` is the profile schema gate. The current validator permits either `measured` or `unsupported` for DOFs and joint limits; this profile's actual values are `unsupported`, and tests already assert those values. Preserve those declarations and do not turn response samples into accepted compiler commands.

The existing compiler allowlist is separate: `rig-mechanical-conformance.cjs` validates exact discrete configurations and uses the pinned 30-bone isolated catalog (1,710 rows). That guard does not make the full-inventory 171-bone report a capability.

**Manifest canonicalization detail:** the current manifest binds the canonical report projection, which removes only top-level `profileSha256`; the current raw report SHA is instead pinned in a constant inside the DWP verifier. For a self-contained durable manifest, add `reportRawSha256` as a manifest field as well as keeping the projection SHA. This does not create a cycle: the manifest still must not contain the profile digest, and the profile can point to the resulting canonical manifest digest. This changes the manifest's canonical bytes/digest and therefore its profile reference. Do not use the old digest after changing manifest paths or fields.

The artifact field is diagnostic provenance only. The canonical report describes observations; it must not become a compiler allowlist. Preserve `descriptor.degreesOfFreedom.status` and `descriptor.jointLimits.status` as `unsupported`, preserve `frames: []` for this conformance compiler, and leave all v3 source/compiler/tests untouched.

## End-to-end test and durability blocker

**Durability alone does not prevent an end-to-end test in this checkout today.** The DWP manifest, report, measurement tool, candidate and licensed source inputs are present locally, and the manifest CLI has already passed against them. A test of the *integrated product path* does not exist yet because the compiler does not load or serialize this manifest. With the implementation delta above, a local end-to-end test could use the present files and candidate bytes without copying or promoting any binary.

**Durability does prevent a repeatable clean-checkout/CI end-to-end run today.** The current manifest/verifier/report/tool/candidate are under ignored `.dwp/`; the source ZIP is under ignored `Personaje/`. The tracked v2 profile records hashes but not asset bytes. In addition, in this worktree `compile-motion-v4.cjs`, `rig-mechanical-conformance.cjs`, `v4-rig-compile-binding.cjs`, their related new tests and the isolated-probe v2 catalog are untracked; profile validator/test/profile files have working-tree changes. A checkout of committed `HEAD` therefore does not contain the current implementation/evidence bundle. The earlier confirmed rev8 export record pins Blender 5.2.3, exporter `82be4e67…07cdf1`, and `--max-texture-size 256`, but that exporter SHA is the modified worktree file; `HEAD` has SHA `0658ffd3…9dfdef`.

There are two distinct gates:

- **Local integrated test after implementation:** feasible with currently available local inputs; no need to publish or copy binaries.
- **Durable independent reproduction from a clean checkout:** blocked until the textual evidence and exact implementation/tool versions are tracked, and a permitted method gives the checkout access to the exact licensed source (or the same bytes through an authorized controlled store). Without that source, CI can verify saved response data and bindings but cannot rerun Blender to regenerate the candidate-bound observations.

No test was run in this mapping pass. The existing stand-alone manifest verifier and the absent compiler integration test are different checks; the former cannot be reported as proof that the product conformance route currently enforces the manifest.
